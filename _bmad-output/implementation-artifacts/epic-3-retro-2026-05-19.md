## What went well

1. **Live-JMRI validation spike before Story 3.1 spec worked exactly as intended.** B1 was the highest-priority Epic 2 action item; executing it before writing a single spec line prevented two would-be mid-implementation surprises (the `/json/` redirect and the heartbeat interval).

2. **Architecture bets held completely.** `websockets.connect()` as an async iterator was exactly right. The `asyncio.TaskGroup` supervision model made `__aexit__` cleanup clean. The per-entity waiter-list/fanout pattern in the architecture spec translated directly to working code.

3. **NFR evidence is now checkable, not just claimed.** NFR1 (latency) has a measurement: 19.6 ms median against a real layout. NFR4 (stability) has a test you can run. NFR5 (disconnect rate) has a formula. Before Epic 3 these were PRD claims; after Epic 3 they're verifiable.

4. **Code review with fresh context caught what tests couldn't.** The lost-wakeup race in Story 3.2 (between early-return check and waiter registration) was invisible to 316 unit tests. The `asyncio.get_event_loop()` deprecation in Story 3.3 was also caught at review, not implementation. Separate-LLM code review remains the only reliable gate for subtle async correctness issues.

5. **In-flight pivot model worked smoothly.** The `websockets` v16 API surprise (process_exception hook returns `Exception | None`, not a delay float) and the ASYNC109 ruff rule conflict were both surfaced with a concrete options list; Mikey's calls were made fast and documented in the architecture and story records.

## What was bumpy

1. **`websockets` v16 API divergence from the architecture spec.** The architecture described `process_exception` as returning the next delay as a float. The actual v16 API returns `Exception | None` (retryable flag). The architecture was written against an older version; caught by the live-JMRI spike, corrected in-session, and the architecture updated with a "Spec revision 2026-05-12" note. No code was written on the wrong assumption.

2. **Story 3.2 had the highest review complexity of the epic.** ~20 findings across three passes. The waiter-list pattern has several genuine async correctness hazards (lost-wakeup race, predicate exception isolation in fanout, `starting_state` capture order) that only surface with careful review. This complexity is inherent — it's not a story-quality issue — but it underlines that Story 3.2 was the riskiest story of the epic.

3. **Architecture doc A1 + A2 carried through three epics.** Two known-wrong items in the architecture doc were flagged at Epic 1, carried through Epic 2, and finally addressed at Epic 3's retrospective. The architecture doc is the source of truth for `create-story` — stale facts in it flow directly into dev agent context.

4. **ruff ASYNC109 rule conflicted with the public `timeout=` API.** Required a mid-story judgment call (per-call-site `# noqa` rather than project-wide disable). Correct resolution, but not anticipated in the story spec.

5. **Story 3.4 wall-clock bug.** First smoke run showed the test ending after the last scheduled disconnect rather than running the full duration. NFR4 is a duration claim, not a disconnect-count claim. Caught in the same session; one idle-fill loop fixed it. Would have produced wrong NFR4 evidence if it had shipped.

## Key insights

1. **The architecture doc is live code, not a one-time artifact.** When implementation diverges from the architecture (Story 3.1's `process_exception` shape, the two known A1/A2 items), fix the architecture in the same session. Don't file it. The architecture is what `create-story` reads — stale facts compound across stories.

2. **Async correctness is uniquely resistant to unit-test-only coverage.** Unit tests verify that code paths exist and behave correctly in isolation. Async race conditions (lost-wakeup, task-leak, cancellation-propagation) only appear under specific scheduling, and code review with fresh eyes is the only gate that reliably catches them. Keep the separate-LLM code review habit for every story that touches async code.

3. **NFR evidence requires real runs, not just claims.** Measuring NFR1 (latency) and NFR4 (stability) required live-JMRI test runs. The 5-minute default for the stability test was specifically designed so the NFR evidence is not painful to gather. Use these tests; don't assume the library is correct.

4. **NCE Simulator turnout echo limitation is now documented and handled.** Turnout state-change commands on simulator-only layouts do not echo back via WS. Sensor commands do. Any story involving WS-confirmed command round-trips (Epic 4) should note this explicitly in the story spec.
