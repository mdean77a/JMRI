## What went well

1. **Architecture-as-prework paid off.** Story 1.2's `pyproject.toml` config, Story 1.3's CI matrix shape, and Story 1.4's PEP 639 SPDX license form were all derived directly from the architecture document. Implementation was essentially zero-rework.
2. **CI green on first push (Story 1.3, six jobs).** No iterative debugging. The pytest exit-5 guard for empty test tree was caught at story-creation time, not during a failing CI run.
3. **PEP 639 SPDX form worked first try with `uv_build`.** No fallback to legacy `{file = ...}` syntax needed. Wheel METADATA emits the modern `License-Expression: MIT` field; license file bundled in `dist-info/licenses/`.
4. **Local quality gates → CI parity.** Story 1.2's local invocation contract lifted verbatim into the CI workflow. Zero translation cost between `uv run` locally and the workflow file.
5. **Story creation caught defects before implementation.** Three gotchas (CI workflow location, pytest exit-5, sprint-status drift) were surfaced during `bmad-create-story` analysis rather than mid-implementation. The exhaustive context-loading step earns its keep.

## What was bumpy

1. **Story 1.1 sprint-status drift.** Implemented on disk but never tracked as a story file; sprint-status.yaml stayed `backlog` while disk had the scaffold. Caught only when starting Story 1.2 and noticing the mismatch. Resolved by flipping 1.1 to `done` retroactively. **No story file exists for 1.1** — this is a small documentation gap.
2. **Architecture diagram defect — CI workflow placement.** Architecture §"Complete Project Directory Structure" shows `python_code/.github/workflows/ci.yml` — but GitHub Actions only reads `.github/` from the repo root. That placement would have produced a silently-ignored workflow. Caught during Story 1.3 creation; documented in the story as "wrong-by-design" and overridden in implementation. **Architecture document NOT yet corrected.**
3. **Tool version drift between architecture prose and lockfile.** Architecture anticipated mypy 1.x and pytest 8.x; `uv add --dev` resolved mypy 2.0.0 and pytest 9.0.3. Both ran cleanly under `strict = true` and `asyncio_mode = "auto"` — but a future story author re-reading the architecture might be confused.
4. **Twine pulled 17 transitive deps.** rich, keyring, cryptography, readme-renderer, etc. Heavyweight for the single `twine check` invocation in Story 1.4, but Story 6.6 will use `twine upload` so the cost is amortized. Acceptable trade-off; called out for transparency.
5. **GitHub Actions first-run warnings.** Cache service transient outage (HTTP 400 / "services aren't available") and Node.js 20 deprecation notice on `actions/checkout@v4`. Both benign, but the user (Mikey, new to GH Actions) reasonably asked if they were a problem. Worth noting that GH Actions UI surfaces warnings prominently and they look like errors.

## Key insights

1. **Story creation is where defects get caught.** The exhaustive analysis step in `bmad-create-story` surfaced more issues than the dev-story implementation step. Worth investing in story creation depth.
2. **"Disk is authoritative for what was built; sprint-status is authoritative for what's been formally tracked."** The reconciliation rule established during Story 1.2 — when they disagree, treat them as separate sources of truth and reconcile explicitly.
3. **Path-scoped CI was the right call.** `paths: [python_code/**, .github/workflows/ci.yml]` keeps JMRI panel-XML, roster, and Jython commits from burning CI minutes. The architectural decision to embed pyjmri in the JMRI repo (rather than a sibling repo) survives because of this filter.
4. **"Local-clean before push" played out in practice.** Architecture's enforcement clause ("CI is the backstop, not the primary gate") was the right framing — every push during Epic 1 was already green locally.
5. **GitHub Actions has visible warnings that aren't errors.** Cache misses, deprecations, etc. surface in the UI annotations panel. New users may worry; experienced eyes triage them as transient or non-blocking. Worth knowing for Epic 2+ when more changes flow through CI.
