## What went well

1. **Architecture as prework paid off again.** The transport/domain boundary, `asyncio.TaskGroup` design, and exception hierarchy were all spec'd in the architecture before a line of code was written. Implementation was execution, not design — zero rework on these structural bets.

2. **mypy --strict held across all 17 source files throughout the epic.** Never broke. The discipline from Epic 1's strict setup is paying compound interest.

3. **Live-JMRI integration loop caught spec surprises early.** Both probe-endpoint mismatches (Story 2.1, Story 2.5) were discovered during the implementation session and corrected before any stale spec could harden into wrong-but-shipped code.

4. **`deferred-work.md` as a running inbox works.** Seven items tracked across code reviews. One resolved exactly when the right story arrived (Story 2.3's `patch_http_factory` deferred item resolved in Story 2.5). The rest are filed for the right future story, keeping debt visible without blocking velocity.

5. **Code review caught a stateful correctness bug that unit tests missed.** The Story 2.5 review identified `_version_checked` not being reset on `__aexit__` — invisible to all 9 unit tests. Fresh-context review remains the only gate that reliably catches stateful lifecycle issues.

6. **Story creation quality.** Exhaustive `create-story` context-loading surfaced open design decisions, provided concrete code sketches, and anticipated gotchas. Story 2.5 had three open design decisions all accepted as proposed defaults — zero back-and-forth, immediate dev start.

## What was bumpy

1. **Two consecutive JMRI endpoint spec mismatches.** Story 2.1 assumed `/json/v5` returns JSON — it returns an HTML debug console. Story 2.5 assumed `/json/v5/version` returns the JMRI application version — it returns only the JSON API version. Both caught live, both recoverable in-session. But the pattern: *assume the JSON v5 API has more surprises ahead for Epic 3*.

2. **Circular import in Story 2.3 not caught during story creation.** `block.py → _parsing.py → _codes.py → block.py (BlockState)` hit at runtime. The story's canonical shape said "add import at top" — that wording would have caused the bug immediately. Resolution (defer parser imports to inside `get_state()`) works cleanly, but this was the one place where story planning didn't front-load a real gotcha.

3. **Roster scope reduction mid-epic.** Dropped `Roster`/`RosterEntry` from the public surface on 2026-05-08 (between 2.2 and 2.3). Applied consistently forward, but it means the epics.md still says "roster" in Epic 2 ACs while the implementation omits it. Minor documentation debt.

4. **Architecture document is now two epics stale on two points (A1, A2).** Still hasn't been updated since the Epic 1 retro. Low urgency, but the gap grows.

---

## Key insights

1. **JMRI's JSON v5 API shape should be treated as "approximate until live-validated."** The architecture's assumed endpoint shapes and response envelopes have been wrong twice. Before Epic 3 adds WebSocket endpoints, verify the actual WS message shapes against a live JMRI before writing specs.

2. **Code review with fresh context catches what tests cannot.** Unit tests verify the code path; fresh-eyes review catches the missing code path (the `__aexit__` reset). The recommendation to use a different LLM for code review is well-founded.

3. **The deferred-work pattern has a correct use and an incorrect use.** Correct: "this is real debt, file it, resolve it at the natural boundary." Incorrect: "defer and forget." The `patch_http_factory` item was resolved at exactly the right moment (Story 2.5) because it was tracked. The `LayoutEntityNotFound` / `KeyError` item should be resolved next time `exceptions.py` is touched — not indefinitely deferred.

4. **`asyncio.TaskGroup`'s `ExceptionGroup` propagation is an API-usability concern for callers.** Story 2.5's `discover()` wraps parallel fetches in a TaskGroup; failure raises `ExceptionGroup`, not bare `JMRIProtocolError`. Documented in the docstring. Epic 3 adds *more* TaskGroup usage (WS reconnect supervision). Worth deciding before Epic 3 whether to unwrap single-exception `ExceptionGroup`s at the API boundary.
