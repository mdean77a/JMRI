## Deferred to post-MVP: API design decisions surfaced during story 6-4 creation (2026-05-24)

- **`Throttle.set_speed(value, *, forward)` forces callers to restate the unchanged half on partial updates — DCC decoders persist last-commanded state, so the API should allow speed-only or direction-only changes** — DCC decoders hold their last commanded speed and direction until a new packet arrives; once a locomotive is moving forward at 0.4 it keeps doing so without further packets. The current `Throttle.set_speed(value: float, *, forward: bool)` signature at `throttle.py:146` requires both arguments on every call, forcing the caller to track the current direction (or current speed) client-side and re-emit the unchanged half. README's migration note (a) at `README.md:125` documents the workaround verbatim: "To change only direction, re-emit the current speed with the new direction; to change only speed, re-emit the current direction with the new speed." A more natural post-MVP API would either (a) make `forward` optional, defaulting to the throttle's last-commanded direction tracked by the `Throttle` instance; (b) split into independent `set_speed(value)` and `set_direction(forward)` methods that send minimal WS envelopes (`{"speed": v}` or `{"forward": d}` respectively); or (c) offer both — keep the current atomic form as `set_speed(value, forward=...)` for callers who want a single packet, alongside the simpler split methods. Defer until after MVP / first PyPI release. Ripples into the README migration table (rows 6–7 at `README.md:115-116`), the Notes block (note (a) at `README.md:125`), and the shipped examples (`back_and_forth.py` / `multi_train_session.py` from Story 6.4). [`python_code/src/pyjmri/throttle.py:146-200`, `python_code/README.md:113-128`]
- **`Roster` is a stub in v1 — JMRI exposes a full roster, basement layout has ~45 locos, but the MVP doesn't surface it** — `pyjmri.roster` at `python_code/src/pyjmri/roster.py:1-9` declares `__all__: list[str] = []` and defines no `Roster` / `RosterEntry` class; `Layout` (`layout.py:197-238`) has 8 collection attributes (turnouts, sensors, blocks, lights, memories, routes, signal_heads, signal_masts) but no `.roster`. JMRI's web server does expose `/json/v5/roster` with a rich per-locomotive schema (DCC address, long/short addressing, road name, road number, model, decoder family, function-bit labels, image references) and the basement `roster/` directory holds ~45 entries used daily by the bundled Jython scripts. The MVP intentionally defers this because (a) throttle acquisition takes a raw DCC address so a typed `Roster` is not on the FR23-FR28 critical path; (b) modeling the schema correctly (especially per-loco function-bit labels and decoder-family metadata) is a non-trivial design exercise; (c) PRD Journey 3's `len(layout.roster)` reference at `prd.md:387-389` and Epic 6.4 AC1's "roster counts" requirement (`epics.md:1011`) were aspirational and Story 6.4 works around the absence by printing the 8 actual `Layout` collections in `hello_jmri.py`. Post-MVP work would add a `RosterEntry` typed class, a `Roster` collection on `Layout` (the 9th collection, dual-name lookup like the others), parallel discovery in `Client.discover()`, a parser in `_parsing.py`, exports in `pyjmri.__init__.__all__`, and ideally a `layout.throttle_for_entry(entry)` convenience that resolves the DCC address from a roster entry (so a user can write `async with layout.throttle_for_entry(layout.roster["UP 5327"]) as t:` instead of hardcoding the integer). [`python_code/src/pyjmri/roster.py:1-9`, `python_code/src/pyjmri/layout.py:197-238`, `python_code/src/pyjmri/__init__.py:35-70`, `_bmad-output/planning-artifacts/prd.md:387-389`, `_bmad-output/planning-artifacts/epics.md:1011`, `roster/` directory at repo root]
