## What went well

1. **Two-phase story design for 6.6.** Splitting "dev-agent-owned build + verify + audit" (Phase A) from "Mikey-runtime publish + hardware validation + tag" (Phase B) cleanly captured the credential-and-physical-action boundary. HALT-handoff worked as designed.

2. **BUILD_SHA discipline at Step 0.** Pinning the wheel's build commit as a recorded value and tagging at that SHA at the end (not at HEAD) prevented subsequent commits — release-check scripts, throttle.py comment update, RELEASES.md, sprint-status updates — from drifting the v1.0.0 tag.

3. **TestPyPI dry-run was cheap insurance.** Rendering verified clean on test before burning the immutable v1.0.0 name on production. The dry-run caught zero issues — and that's the win shape (low cost, infinite upside if it had caught something).

4. **Hardware-mode "keeps" outcome confirmed Story 5.1's design.** The keep-alive no-op stub was the right call. 30 s silent hold did not drop the throttle on JMRI 5.14.1 / NCE USB. Comment-only update at `throttle.py:316-345` records the verification.

5. **Long-run `rss_delta=-5.1MB`.** Negative memory delta over 1 hour; 5 clean disconnect/reconnect cycles; zero leaked tasks or FDs. Validates Story 3.1's reconnect machinery and Story 3.2's waiter cleanup end-to-end.

6. **Smoke install proved the wheel works for downstream users.** `NT100 CLOSED → THROWN` against a PyPI-installed wheel in a fresh venv with no dev-tree pollution. FR40 / AC3 satisfied end-to-end.

7. **Walking Phase B with the operator step-by-step.** Confirm-at-gates + execute-mechanical-steps cadence kept the immutable publish from being a leap-of-faith.

8. **CONTRIBUTING.md release checklist worked as an enforceable script.** Phase B was "follow the documented procedure top to bottom" — not "figure out what to do." Where the doc was ambiguous, we paused, decided, and moved on.

## What was bumpy

1. **`ruff format --check` is a separate CI gate and I missed it.** Added `release-check/release_*.py` with `ruff check` passing locally but `ruff format --check` not run. CI failed on comment-alignment whitespace. Follow-up format-fix commit cleared it. Lesson saved to memory (`feedback_ruff_format_gate.md`): both gates, every time, on any new/edited Python in `python_code/`.

2. **Story 6.6 Phase B Step 6 "keeps" branch creates a documented wheel/tag comment asymmetry.** Updating `throttle.py:316-345` with the hardware confirmation happens *after* the wheel was built from `bd4435d`. Story spec is clear that rebuild is only required on "drops" (Step 6a), but the spec could be more explicit that "keeps" intentionally leaves a one-paragraph cosmetic difference between the wheel source and the tag commit.

3. **Integration test flake on `IS1`.** First run of integration suite during Phase B Step 4 failed `test_sensor_wait_change_median_latency_under_100ms` from inter-test interference on the shared internal sensor `IS1`. Isolated re-run passed (15.5 ms median, well under NFR1's 100 ms). Second full-suite run also clean (37.9 ms median). Cosmetic-tier test hygiene gap; not a release blocker.

4. **TestPyPI vs production PyPI token confusion (story-spec gotcha #6 hit in practice).** First `uv publish --publish-url https://test.pypi.org/legacy/` returned 403 because the token was minted on `pypi.org`, not `test.pypi.org`. Same `pypi-…` prefix, identical-looking, separately rejected by the test site. The spec called this out — and we still hit it. Cost: 5–10 minutes and a token regeneration. Worth louder warnings.

5. **Stale memory at `/bmad-help` invocation.** Memory entry said Story 6.6 was still awaiting code review when in fact CR completed 2026-05-25. Wrong next-step recommendation. Mikey corrected via the story file's change log. Lesson: memory is point-in-time; for status/dates/SHAs, always verify against on-disk source before recommending action.

6. **Long-run duration deviation flagged then reverted.** Operator initially suggested 300 s instead of 3600 s. Flagging *why* the documented gate is 3600 s (strictly stronger RSS-delta signal, 5 disconnect cycles vs 1) led to the right call: full hour. The `rss_delta=-5.1MB` result would have been masked under the 300 s relaxed RSS budget.

## Key insights

1. **"Phase A / Phase B" is the right model for any release-bearing story.** Future releases (v1.0.1, v1.1.0, etc.) should follow the same two-phase shape rather than re-deriving where the agent stops.

2. **"BUILD_SHA at Step 0" is the safety rail for divergent commits during release.** Capture early, hold through close-out. Apply to every release.

3. **Polish-discipline memories compound.** `feedback_polish_matters.md`, `feedback_ruff_format_gate.md`, `feedback_use_uv.md` each prevent a class of repeated mistake. The format-gate memory was *born* from this epic.

4. **CONTRIBUTING.md release checklist is enforceable when it lists concrete commands and physical actions (Story 6.5 AC3 discipline).** Aspirational prose would not have worked.

5. **The README serves three distinct readers from one document.** Quickstart for "does this work" reader; Limitations for "what won't this do" reader; Migration table for "I have Jython, can I switch" reader. All three render on the PyPI page.

6. **Open-loop honesty (FR22) propagated through the entire release narrative.** "Confirmed unnecessary" in `throttle.py`, "no source change required" in `RELEASES.md`, "the v1 no-op keep-alive stub is correct" in the GitHub release notes. The honesty discipline scaled.
